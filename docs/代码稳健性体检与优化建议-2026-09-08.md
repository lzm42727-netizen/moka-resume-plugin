# Moka 智能简历筛选助手 · 代码稳健性体检与优化建议

> 日期：2026-09-08 ｜ 基线：`npm run check` 全绿 385/385（v1.6.17）
> 方法：四路并行只读代码审计（background/SW+lib、content 隔离世界、inject 桥与契约、popup 侧栏）+ 关键事实人工核验。
> 结论速览：**未发现「必崩级」确定性缺陷**，历史事故根因（跨岗串档、回填中断、applyingPreset 卡死）已修复并有契约测试锁住。剩余风险集中在**四类系统性短板**：① 工程防护没覆盖最大入口文件；② 扩展热更新下的重复执行/重复监听；③ 切换/恢复/停止等异步路径缺互斥与容错；④ 存储写入与桥接协议的可观测性不足。
> 本报告只读产出，未改动任何代码；版本号未变（1.6.17）。

## 二、P1 优先修复项（按风险排序）

### P1-1 快速切岗无互斥锁 → 空表单可能覆盖真实存档（数据丢失风险最高）
- **位置**：`popup/popup.js:329` `switchJobPreset`；触发方 `:1706`（loadJobs 内）与 `:1721`（职位下拉 change，fire-and-forget `.then()`）
- **问题**：`switchJobPreset` 内 `await saveJobPresetFor(prevJobId)`（保存旧岗）与 `resetJobPresetForm`（清空表单）、`restoreCurrentJobPreset`（填回新岗）是**串行 await 但无函数级互斥**。`applyingPreset` 锁与 `presetFormJobId` 跨岗闸门只保护"表单正装着谁"，不阻止两个 `switchJobPreset` 交错：A→B 还没 restore 完、用户已点 B→C 时，B→C 的 `saveJobPresetFor(B)` 会在表单已被清空、B 的内容还没填回的窗口期执行 → **用空/半成品表单覆盖 B 的真实存档**。手动切岗（1721）与页面 SPA 切岗触发的 loadJobs（1706）之间也没有互斥。
- **建议**：给切岗加一把专用互斥锁（复用 `loadJobsInFlight` 范式），change 处理器先 `await` 在途切换完成再发起；或在清空前把上一岗表单快照缓存、保存以快照为准。推荐最小改法：

```js
let switchInFlight = null;
function switchJobPreset(prevJobId, targetJobId, label) {
  if (switchInFlight) return switchInFlight.then(() => switchJobPreset(prevJobId, targetJobId, label));
  switchInFlight = (async () => { /* 原函数体 */ })().finally(() => { switchInFlight = null; });
  return switchInFlight;
}
```
- **工作量**：S ｜ **回归测试**：popup-ui 断言 switchJobPreset 存在在途去重/排队逻辑

### P1-2 window load 初始化链无 try/catch → 一次存储异常令搜索/导出永久失绑
- **位置**：`popup/popup.js` window load 初始化（`await refreshResultsAndJobContext()` → `bindResultFilters()`），约 `:2402-2413`
- **问题**：初始化是一长串 `await`，无任何 try/catch。只要其中一环（storage 读取/消息）reject，后面的 `bindResultFilters`（结果区搜索框、筛选标签、导出按钮的事件绑定）永不执行，**功能半残且无明显报错**。
- **建议**：每条 `await` 独立 try/catch（或 `Promise.allSettled`），并保证 `bindResultFilters()` 与按钮禁用复位必定执行；初始化失败给可见提示。

### P1-3 停止/暂停后，在途评分 worker 把任务状态写回 running
- **位置**：`content.js` `stopScreening`（约 `:1209`）→ `finishScreeningJob('stopped')` 未 await；worker 内 `patchScreeningJob({status:'running',…})`（约 `:2278`）
- **问题**：用户点停止后，仍在 `await scoreViaBackgroundWithRetry`（最长 120s）的 worker 返回时会再次把快照状态**写回 `running`**，界面/后台误判任务还在跑，续筛会错误恢复。
- **建议**：`patchScreeningJob` 写 `running` 前校验 `isScreening && epoch === screeningEpoch`，否则丢弃回写；或 `finishScreeningJob` 采用"终态优先"的原子写。

### P1-4 pullResults/applySnapshot 无「按岗 + 时序」校验 → 乱序响应覆盖当前列表
- **位置**：`popup/popup.js` `pullResults`（约 `:2850`）、`applySnapshot`（约 `:2857`，`resultState.items = mergeFeedbackIntoViews(incoming)`）
- **问题**：`pullResults` 无 in-flight/序号保护；tab `onUpdated/onActivated` 高频触发时，A 岗滞后响应可能覆盖 B 岗当前结果（列表串岗/丢最新），仅靠 `resultMismatch` 横幅提示。
- **建议**：请求时记录 `requestJobId = currentJobId()` + 自增序号，回包先比对"仍是当前岗且是最新一次请求"再应用。

### P1-5 候选人分页抓取零重试 → 单页瞬错整轮中止
- **位置**：`content.js` `fetchAllApplications`（约 `:1559`，`if (!resp.ok) throw …`）
- **问题**：数百页列表任取一页偶发 429/503/超时即 throw，整轮筛选转 `awaiting_resume`。千人规模下几乎必然发生。
- **建议**：单页 `fetchWithTimeout` 加重试 + 指数退避 + 上限；429/空响应专项识别；超限才中止并保留已完成部分。

### P1-6 扩展热更新后 inject/content 重复注入：双包 fetch/XHR、双份监听
- **位置**：`inject.js:13`（IIFE 起点，无 `window.__moka*` 守卫）、`inject.js:327-395`（fetch/XHR 原型包裹）；`content.js:1116`（onMessage addListener）、`:611`（window message）、`:1403`（popstate）、`:3640`（init 调用）
- **问题**：MV3 扩展更新/重载时，已打开页面的旧 MAIN-world 包装与旧监听残留，新脚本再次执行 → 请求被捕获两遍、消息双发、批量推进存在重复提交风险。
- **建议**：inject IIFE 顶部 `if (window.__mokaInjectLoaded) return; window.__mokaInjectLoaded = true;`，XHR 原型加 `__mokaWrapped` 标记；content `init()` 加"仅执行一次"守卫或先 `removeListener` 再注册；与 background 做 protocolVersion 握手，契约不符时降级。

### P1-7 background importScripts 无容错 → 单个库顶层抛错整体瘫痪
- **位置**：`background.js:22-28`（必需库 importScripts 均无 try/catch，仅 config.local.js 有）
- **问题**：任一必需库在顶层 IIFE 抛错（语法/运行时错误），整个 SW 加载失败，所有 onMessage/onAlarm 不注册，无降级。
- **建议**：逐个 try/catch + `console.error(模块名)`；保留 config.local.js 容错并推广到全部 import。

### P1-8 background 并发评分无 in-flight 去重 → 重复扣费与结果抖动
- **位置**：`background.js` `handleScoreCandidate`（约 `:524`）+ 内存 `scoreCache`
- **问题**：同一 profile 的并发请求双双 miss 缓存 → 各发一次 LLM、各写缓存；结果不确定时 content 拿到哪份取决于谁先回。
- **建议**：`Map<cacheKey, Promise>` in-flight 锁，并发命中同 key 复用同一 Promise。

### P1-9 MAIN-world 桥接消息缺 nonce/结构校验（同源 XSS 面）
- **位置**：`content.js:611-651`（监听 `moka-inject`）；`inject.js:400-422`（监听 `moka-content`）
- **问题**：content 仅校验 `event.source === window` 与 `source === 'moka-inject'`。inject 与 content 共享同一 window，页面内任何脚本（含 Moka 自身 XSS）可伪造 `detail-data`/`assignment-request`/`member-data`，篡改候选人经历与"姓名↔id"分配映射 → **误把候选人推进给错误用人部门**。
- **建议**：对驱动写操作的桥接消息加 nonce（content 请求带 nonce、inject 回带同一 nonce）；`detail-data` 做最小结构校验（含 application id 且能 `detailBelongsTo` 当前页）。

### P1-10 存储写入失败全静默 → 缓存/续筛状态丢失无痕
- **位置**：`background.js:126`（`schedulePersistLlmCache`）、`:209`（`persistPendingMokaToDisk`）的 `chrome.storage.local.set` 无 `.catch`/回调/lastError 检查
- **问题**：写入失败（配额/被回收）静默丢失。LLM 缓存丢失 → SW 重启后重复扣费；pendingMoka 丢失 → 页面刷新后的续做操作静默失效。
- **建议**：统一封装 `storeSet(key,val)`：`.catch(e => console.error(...))` + 读 `lastError`。popup 侧同类（开筛前落盘 `:1926`、autoSave `:1061`）失败时给 toast，**不要显示"已保存"**。

## 三、P2 健壮性建议（按主题归并）

### 工程与质量门禁
- **P2-1｜lint 未覆盖 4 大入口文件（1.6.17 事故的同类漏洞温床）**：`package.json` `lint` 只跑 `eslint lib tests scripts`，**popup/popup.js、content.js、background.js、inject.js 全不在检查范围**——上一轮 `setMultiSelectOptions` 未定义调用正是因此漏网（语法合法、lint 不查、单测正则没锚到）。建议：① 把这些文件纳入 eslint（配 `/* global chrome, window, document */` 等环境注释或 globals 配置）；② 加一条轻量静态检查「同文件内被调用的标识符必须在本文件或白名单（chrome/window/document/console/Moka*）中有定义」，直接锁死"调用已删除函数"这类 bug；③ prettier `format:check` 同样扩围。
- **P2-2｜契约注册表缺口**：`flushPluginLog` 实际在用（popup:1343 send、content:1267 handle）但不在 `lib/contracts.js` ACTIONS 内；`hasLastResults/showLastResults/getRequestLog/getBatchAssignContext` 4 个动作"只被处理从未被发送"（疑似死代码）。建议补登记 + 清理死 handler。
- **P2-3｜inject↔content 的 window.postMessage type 完全游离于契约外**：search-request / detail-data / assignment-request / member-data 等 13 个桥接 type 无注册表、无两端对称单测 → 一端加、一端忘，静默断链。建议新增 `lib/bridge-contracts.js` 并在 content-boot/content-log-contract 测试做"两端 type 对称"断言。

### 生命周期与泄漏
- **P2-4｜background alarm 泄漏**：`keepaliveTabId` 归 null 后每分钟空唤醒不停（`background.js:437-445`）。建议 onAlarm 里 `if (keepaliveTabId == null) { chrome.alarms.clear(name); return; }`。
- **P2-5｜LLM 缓存 400ms 防抖落盘窗口**（`background.js:121-131`）：SW 在窗口内被回收则丢最近一次写入 → 重复扣费。建议关键写直落或 `onSuspend` 兜底 flush。
- **P2-6｜XHR 拦截每次 send 都 addEventListener('load') 不移除**（`inject.js:381-391`）：同实例复用会累积监听。建议回调首行 removeEventListener。

### 性能与关键路径
- **P2-7｜拦截器在页面主请求关键路径同步刮 DOM + 全量 JSON.parse**（`inject.js:280-318`、`:349`）：拖慢页面请求与主线程；越权解析任意同源 JSON 响应（隐私面）。建议刮取/解析移出关键路径（queueMicrotask/节流）、响应体大小与频率设硬限、只处理 mokahr.com 同源响应。
- **P2-8｜fetchAllApplications 无职位上下文时盲拉旧模板**（`content.js:1537`）：URL 无 jobIds 且无当前配置时回退旧 capturedRequest，可能拉错职位。建议无明确职位上下文时拒绝开筛并提示。
- **P2-9｜enrichCandidate 详情抓取无重试**（`content.js:1947`）；`requestAssigneePairs` 超时仅 4s（`:433`）。建议各补一次重试/提超时。

### 状态与可观测性
- **P2-10｜`reconcileJobTypeWithLabel` 设 `applyingPreset=true` 无 try/finally**（`popup/popup.js:321`）——历史 bug 同类形态，建议统一 finally 解锁。
- **P2-11｜顶层 `getElementById` 无空值守航**（`popup.js` 顶部编辑器/监听绑定区）：脚本置于 body 末尾目前安全，但 HTML 一重构即整段瘫痪。建议统一 `safeEl(id)` 封装；`MokaPersist` 依赖处加 `window.MokaPersist &&` 判空。
- **P2-12｜`catch(()=>{})` 静默吞错分散多处**（popup:1926、inject:37/46/341 等、`readAssigneeConfirmedAt` 归零、`flushPluginLog` 返回 null）：失败不可见。建议统一收敛为 `console.warn`/pushPluginLog。
- **P2-13｜capturedRequest/capturedAssignment 缺来源身份戳**（`capture.js:129-136`）：窗口期回退旧职位模板。建议记录来源 pipelineId+时间戳，开筛前校验。
- **P2-14｜job 快照读-改-写无锁（lost update）**（`content.js:2087-2106` + worker `:2278`）：4 worker 并发写 status/usage 后写覆盖。建议状态写入串行化或用累加器。
- **P2-15｜resumeTextCache 只存内存不落盘**（`background.js:452`）：SW 重启后重新 fetch 附件（额外延迟/额度）。建议并入 LLM 持久化键。
