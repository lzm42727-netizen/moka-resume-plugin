# 本岗要求清单（方案 D）优化方案

> 状态：**待评估，未开工**  
> 背景：结果卡会出现「重要 −N」扣分，但配置页「其他必备」里看不到对应项，招聘官心智不一致。  
> 检查点：已推送 `v1.6.1` / `v1.6.2`（含本岗校准、必备满扣 −30）。

---

## 1. 一句话目标

把「必须 / 重要 / 加分」收成**本岗可编辑的一份清单**；开始筛选与综合分**只认这份清单**，不再背地使用 JD 里未确认的 importantHaves。

---

## 2. 现状问题（为何要改）

| 用户看到的 | 系统实际做的 |
|------------|--------------|
| 配置页只有「其他必备」芯片 | 开筛时 AI 解读 JD，另生成 `importantHaves` / `niceToHaves` |
| 以为只按芯片 −5 | 重要项未满足每条 −3，卡片标「重要」 |
| 校准「加入必备项」只动芯片 | 重要项仍可能来自 JD 缓存，和校准脱节 |

根因：评分尺子 = **显式配置 ∪ 隐式 JD 画像**，配置页只露出一半。

---

## 3. 方案 D 要长什么样

### 3.1 配置页：本岗要求清单（三栏）

替换/升级现有「其他必备」单一芯片区：

1. **必须**（未满足 −5，最多 6）— 对应当前「其他必备」+ 可勾选的 JD 建议  
2. **重要**（未满足 −3，最多 6）— 现有暗扣来源，改为可见可删  
3. **加分**（未满足不扣分，最多 6）— 仅展示缺口，不影响综合分  

每栏：芯片编辑（增/删/改文案），与现有 chip editor 一致。

硬性条件（学历/院校/年限等）**仍单独一块**（结构化，默认红标不扣分），不并进三栏，避免和「可忽略必备」搅在一起。

### 3.2 JD 预填 = 建议，不是生效

点「按 JD 预填」或首次开岗：

- AI 仍产出 must / important / nice  
- **写入清单草稿或「建议区」**，默认策略待评估（见 §5）  
- 招聘官可删改；点「保存当前筛选条件」后落本岗 preset  

开筛时：`jobSpec.mustHaves / importantHaves / niceToHaves` **只来自本岗清单**，禁止再用「未进清单的 JD 原文」去扣分。

### 3.3 结果卡与忽略

- 「必须 / 重要」未满足：继续可「忽略」加回该条扣分（逻辑不变）  
- 「加分」未满足：仅说明，无忽略按钮（或不展示为扣分态）  
- 卡片提示改为：`匹配度 xx · 必须 −a · 重要 −b`（有则显示）  
- 文案标明来源时可写「本岗要求」，避免「来自神秘 JD」感  

### 3.4 本岗校准怎么接

- 「采纳必备」默认写入 **必须** 栏（可在建议上选写入必须/重要）  
- 校准不再与「看不见的 important」打架  
- 保存成功 = 写清单 + 本岗 preset（与现行为一致）

### 3.5 数据与兼容

本岗 preset 扩展字段（示意）：

```text
requirements: {
  must: string[],        // ≤6
  important: string[],   // ≤6
  nice: string[]         // ≤6
}
```

迁移：

- 旧 `mustHaves` → `requirements.must`  
- 旧预设无 important/nice → 空数组（**不再**在开筛时自动灌 JD important 来扣分）  
- 可选：第一次打开某岗若 must 有值、important 为空，提示「可点预填补全重要/加分」

## 4. 关键改动面（评估用，非排期）

| 区域 | 文件（预计） | 改什么 |
|------|--------------|--------|
| 配置 UI | `popup/popup.html/css/js` | 三栏芯片；预填写入三栏 |
| 持久化 | `lib/persist.js` | preset 增 `requirements`；读写兼容旧 `mustHaves` |
| 开筛合并 | `content.js` | 取消「AI important 隐式进分」；只传清单 |
| 评分展示 | `lib/score.js` / `lib/match.js` | 文案；`renderRequirementChecklist` 只渲染清单 |
| 校准 | `lib/calibrate.js` / popup | 采纳目标栏：必须/重要 |
| 测试 | `tests/*.test.js` | 迁移、开筛只认清单、扣分分档 |
| 说明 | `使用说明.html` / README | 同步心智 |

**刻意不做（本方案边界）**

- 不改四维权重模型  
- 不改结构化硬筛 tag 模式  
- 不把学历等结构化项搬进三栏

## 5. 待你拍板的决策点

请评估时尽量对下面选项表态（可多选备注）：

1. **JD 预填默认行为**  
   - D1：预填进三栏但**未保存前不用于历史岗**（仅表单）  
   - D2：预填后自动写入本岗 preset（省事，易「没看清就被扣」）  
   - D3：预填进「建议」，需逐条/一键「加入清单」才进栏（最稳，多一步）  

2. **AI 抽的 must 与手写必须冲突时**  
   - 合并去重（现状倾向）  
   - 手写优先，AI 只进建议  

3. **重要项是否允许为 0 条就开筛**  
   - 允许（推荐：完全由招聘官决定）  
   - 不允许（强迫先预填）— 不推荐  

4. **旧岗位已有大量「重要暗扣」习惯**  
   - 一刀切：升级后只认清单（推荐，心智干净）  
   - 过渡期：若清单 important 为空则回退旧 JD important（易再混淆）— 不推荐  

5. **本岗校准默认写入**  
   - 必须栏（推荐）  
   - 重要栏  
   - 弹层自选

## 6. 成功标准（做完怎么验收）

1. 配置页能看见并编辑本岗全部会扣分的「必须/重要」文案。  
2. 结果卡任意「重要 −N」条目，都能在配置清单重要栏找到同源文案（或用户刚删则不应再扣）。  
3. 清空重要栏后重筛，不应再出现「重要 −N」（除非用户又预填/加回）。  
4. 保存本岗 → 换岗再切回 → 三栏恢复一致。  
5. 单测覆盖：迁移、只认清单、满 6 条封顶。  

---

## 7. 风险与代价

- 配置区变高：侧栏要折叠或 Tab（「硬性 | 要求清单 | 权重」）防一屏过长。  
- 首次预填若默认写满重要，仍可能「以为没配」— 故倾向 **D3 或 D1 + 强提示**。  
- 与「只按芯片扣分」的 A 案比，D 更重，但保留分级扣分能力，和现网评分语义更连续。
