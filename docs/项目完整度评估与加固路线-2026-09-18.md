## 三、工程质量现状

### 3.1 已到位的（不必再投入）
- `npm run check` 四连门禁（syntax → version → lint → test）全绿可提交；lint 覆盖四大入口文件（no-undef 锁死死调用）；dead-export 白名单为空；契约注册表 61 个 ACTION 有对称测试；popup 无 innerHTML 注入候选人数据（9 处 innerHTML 全为清空/静态串）。

### 3.2 测试结构失衡（质量短板的核心）
- 543 个测试中，**popup-ui（364 处）/ background-contract（104）/ bridge-contract（81）/ content-log-contract（42）/ content-boot（32）全部是「正则匹配源码文本」**——实现重写（语义等价）会误红，行为回归（文本还在）不红。
- 零行为测试的高危区：**background WS 重连/心跳全部时序、feishu-bridge/server.js 全部**（顶层直接执行、无法 require）、回执 `replied` 状态机、popup 渲染交互、content 的 fetchPageWithRetry 并发。
- 「改了实现正则不会红」的典型：把 server.js 的 `70000` 提成常量改名即绕过 `/70000/` 正则锚。

### 3.3 工程化短板
- prettier 只覆盖 `lib/contracts.js` 一个 lib 文件，与 lint 范围不对称；
- CI 只跑主仓，feishu-bridge（独立 package.json）完全不装不测；
- pack.js 打包不含 config.local.js（发布包「部署摘要锁定」静默消失，属已知取舍但无警告）；依赖系统 `zip` 命令（Windows 不可用）。

## 六、建议路线（全部为渐进式，不改变现有功能语义）

### 6.1 加固批次（代码加固）

**第一批「存储与身份统一」（建议 v3.3.0，风险最高收益最大）**
1. content 侧建 `assigneeStoreWriteQueue`（Promise 队列），收编 R1 四条写链路；popup 侧 `JOB_PRESET_STORAGE_KEY` 写入统一走一个带队列的 `writeJobPreset(jobId, mutator)`，收编 R5（确认章与自动保存互斥）；
2. `loadAssignmentForCurrentPipeline` 加**名章校验 + 别名键回退**：`captures[pid]` 名章与页面职位名不符时，按当前页面职位名扫别名键/全表精确匹配（修 R2）；批量推进执行前把「模板职位名 = 当前页面职位名」写进运行日志留痕；
3. `persistAssignmentEntry` 的 set 补 lastError 检查，失败 done(false) + 日志（修 R4 尾巴）；
4. background `feishuRecommendByScore` 选 tab 改为「URL query 中 pipelineId 精确匹配优先」，并在下发指令时把卡片所属职位名带给 content 二次校验（修 R3）。

**第二批「Bridge 可测性与安全」（建议 v3.3.x~v3.4.0）**
5. server.js 顶层加 `require.main === module` 守卫 → 用 node:test 补 WS 协议行为测试（死链探测、回执单发、连点去重）（修 R6①）；
6. Origin 白名单收窄到本扩展 ID（chrome.runtime.id 从 background 握手带入 config）+ 可选一次性 token（修 R6②）；
7. bridge.log 加简单轮转（>10MB 改名 .old）+ LaunchAgent 补 ThrottleInterval（修 R7/M12）；
8. config.json 权限 0600；回执失败重试 1 次（修 M3/M4 部分）。

**第三批「生命周期与一致性收尾」（随版本顺带）**
9. LLM 缓存关键写直落 + onSuspend 兜底 flush（M1）；`feishuBridgeManualDisconnected` 落 storage.session（M2）；scheduleContentResume 改 alarm（M5）；keepalive 重连补试（M6）；
10. storeRecommendNames 补名章守卫（M8）；别名键诊断展示与清理豁免（M9）；rememberJobPipeline 入写队列（M7）；
11. 权限最小化：删 `scripting`/`activeTab`，openai/anthropic 移 optional（M11）——**注意发布前回归一次自定义网关授权流程**；
12. normalizeWeights 双实现统一命名（M10）；四套提示条收敛为一个 dock toast（M14）。

**第四批「结构性」（单独排期，收益是长期可维护性）**
13. popup.js 按功能域拆 11 个模块（job-preset 660 行 / results-view 900 行 / batch-assignee 540 行等，拆前先把 30+ 模块级可变全局收进各域 state 对象）；
14. 「正则锚」测试逐步行为化：优先 background WS 时序与 server.js 协议（第二批解锁后）、popup 渲染（可用 jsdom 或最小 DOM stub）；
15. Bridge 协议动作入 contracts 注册表 + 对称测试（M15）；prettier 全覆盖单独一个格式化提交（避免噪音混入功能 diff）。

### 6.2 功能优化建议（按 HRBP 使用价值排序）

1. **面试官负载均衡**：批量推进前拉取各面试官近期已分配候选人数量，推荐对象面板给出「建议人选」（把 1:4 师生比这类隐患在分配端就消掉）——与用户的人才盘点本职直接呼应；
2. **筛选结果统计增强**：结果页导出 CSV 已有，可加「本岗漏斗摘要」（各决策档人数/通过率/平均分/花费），或一键生成部门维度周报（复用既有 talent-review 分析习惯）；
3. **JD/门槛变更检测**：职位理解与校准规则生成后，检测 Moka JD 文本变更即提示「校准可能过期」，避免旧规则误导新评分；
4. **多职位并行筛选看板**：当前按岗串行，可在结果聚合层做跨岗对比视图（同一候选人在多个岗位的评分对照）；
5. **飞书卡片轻交互扩展**：回执卡片加「查看评分明细」深链（定位到具体候选人卡片），复用现有 URL 通道；
6. **模板/偏好库**：跨岗位复用门槛组合（如「实习生通用门槛」一键套用），减少每岗手工配置。

## 八、附录：与外部评估（2026-09-18）的对比与合并结论

同日收到另一份独立评估，两相交叉验证后的结论如下（已并入 §6 路线）：

**互相印证的重合区**（两边独立得出，可信度高）：入口文件过重需拆分、存储写入统一封装、Bridge 本地鉴权 token、optional host 权限过宽、敏感信息明文落盘、缺端到端验证且测试偏契约/静态。

**对方抓到、本报告漏掉的（已采纳）**：
1. **README 版本漂移**（要点停在 v3.1.0、manifest 3.2.2）——已核验属实；README 此前是版本门禁的漏网点，已纳入 `check:version`（v3.2.3 落地）；
2. **健康检查/诊断页**——排查快照偏开发者视角，普通 HR 需要一眼可懂的体检入口，列入第三批；
3. **Moka DOM selector 适配层（lib/moka-dom-adapter.js）**——把按钮文案表/弹层选择器集中为单一模块 + fixture（1.9.9 点错导航按钮一类问题的结构性解法），列入第三批；
4. **性能/容量保护**（大批量人数软提示、单轮预算上限、费用预估确认），列入功能优化。
