一、项目概览

定位：面向招聘 HR 的 Moka ATS 智能筛选插件。在 Moka 候选人列表页批量拉取简历 → 本地核对硬性门槛 → 调用 LLM 评估岗位匹配度 → 在 Chrome 侧栏给出决策分与推进档位 → 支持"推荐给用人部门 / 淘汰"的反馈闭环与本岗校准。

维度情况
技术栈原生 JavaScript（无框架）、Chrome Extension Manifest V3、Service Worker、双 World Content Script（MAIN + ISOLATED）、Chrome Side Panel、OpenAI / Claude / OpenAI 兼容 LLM API、Node.js node:test
规模约 17,768 行；lib/ 8 个纯逻辑模块、tests/ 10 个测试文件、2 份 HTML 文档、docs/ 规格与计划文档齐全
工程史git 30+ 提交，从 v1.0 迭代至 v1.6.3，分支 feature/gate-ai-match-scoring 上仍有未提交改动
核心文件background.js（1,085 行，LLM 调用层）· content.js（2,623 行，页面自动化）· popup/popup.js（2,862 行，侧栏 UI）· lib/*.js（评分/捕获/持久化/匹配/反馈/校准）

3.2 功能亮点

  • 先证据后打分的评分规格：要求模型先输出经历证据（experienceEvidence）再给匹配分，显著降低"凭印象打分"的幻觉，配合"先证据后匹配分"的设计文档锁定。
  • 门槛封顶不托底：未过门槛决策分 = max(0, 49 − 7×条数)，同时把"经历匹配"单独展示，避免硬门槛把本来匹配的人压成 0 分，信息不丢失。
  • 防串号设计：详情接口按 URL 精确规则识别 + 顶层 id/candidateId 校验，规避了头像 OSS 签名链接导致的"数据串号"这一高发坑。
  • 反馈学习闭环：HR 的"推荐/淘汰"决策会形成偏好快照注入下一轮评分（feedbackPromptBlock），并生成"加入重点看/放宽门槛/去掉加分项"等可采纳建议——这是从"工具"到"助手"的关键跃迁。
  • 工程可验证：每个迭代都带 spec + TDD 计划 + 全量测试，prompt 有版本号并随缓存 key 联动，保证升级不串数据。

四、代码质量评估

4.1 优点

  • 分层清晰：lib/ 8 个纯逻辑模块全部采用 IIFE + UMD 双环境模式（浏览器挂 root.Moka*，Node 下 module.exports），一套代码同时支撑扩展运行与单测。
  • 防御式编程到位：网络请求统一带超时；LLM 调用指数退避重试（429/5xx/网络错误）；所有存储读写 try/catch；数据进出均经 sanitize/归一化，字段都有上限与默认值。
  • 健壮的模型输出解析：stripThink 去推理块 → 平衡 JSON 扫描 → 截断 JSON 修复（repairTruncatedJson）→ 正则宽松抽取逐级兜底，能扛住推理型模型的"思考 + 截断"。
  • 缓存策略成熟：评分/JD 缓存带 TTL（7 天）与容量上限（500），内存 Map + chrome.storage 双写，SW 重启不重复扣费；解析失败不写缓存。
  • 注释与文档质量高：中文注释解释"为什么"（如为什么不用 patch history、为什么清游标、为什么在 background 发请求规避 CSP）；docs/ 有规格（含非目标、验收算例）与分步实施计划。
  • 边界处理细：评分失败不卡整轮（记错误分继续）；筛选心跳防"假活"卡死；Moka 操作跨页导航有 120s 过期保护；换岗不误杀。

4.2 问题与风险

级别问题说明与影响
高三个单体大文件content.js（2,623 行）、popup.js（2,862 行）、background.js（1,085 行）承载了流程、DOM、消息、状态机、存储等全部职责，难以单测、易产生隐性耦合与 TDZ/全局状态问题。
高无工程化基础设施没有 package.json、无 lint（ESLint）、无格式化、无 CI、无构建/打包脚本、无 CHANGELOG。测试只能靠约定命令运行，新成员或换机器成本高。
中浏览器侧逻辑无自动化测试content.js 覆盖率 28.8%、moka-actions.js 49.7%。UI 与页面自动化（DOM 点击、消息路由、筛选状态机）完全依赖人工回归，迭代回归风险集中在这些区域。
中隐式全局依赖模块间通过 window.MokaScore / MokaMatch 等全局挂载互相引用（如 match.js 里直接调 MokaScore），缺少显式依赖注入；改名或重构容易漏。
中计分规则复杂度过高"门槛封顶 49 − 7×N + 加分看 3×N ≤ 15 且仅匹配≥50 计入 + 加分晋级 + 忽略恢复重排"的组合逻辑横跨 score/match/persist/feedback/calibrate 5 个模块，字段多达 20+（bonusApplied/bonusPromoted/advanceReason…），维护和向新同事解释的成本高。
低隐私边界候选人画像会发送到用户配置的第三方 LLM（README 已声明）。内网合规场景需更严格的脱敏/自托管指引；无敏感字段屏蔽选项。
低主线程性能inject.js 劫持全局 fetch/XHR，content 有 1.5s 轮询换岗检测；大列表（数百人）下 DOM 更新与消息频繁，未做虚拟滚动/批量节流。
低魔法数与硬编码CONCURRENCY=4、MAX_PAGES=300、49/7/3/15/50/80 等散落各处，虽多数有常量注释，但未集中成配置。

五、完整优化建议

优先级说明：P0 近期且影响可靠/安全；P1 中期提升工程质量与体验；P2 长期架构与能力扩展。

5.1 P0 · 近期必做

  1. P0补齐工程化底座：新增 package.json，固化 npm test（node --test tests/）、npm run lint、npm run check（全量 node --check）、npm run build（产出 dist/ 打包 zip）。接入 ESLint（推荐 eslint:recommended + no-undef）与 Prettier，配置 git pre-commit hook，一条命令即可完成"测试+语法+打包"，消除换人/换机成本。
  2. P0给浏览器侧逻辑补集成级测试：引入 Playwright 扩展测试（chromium 已支持 --load-extension），对 content.js 的筛选状态机、消息路由、popup 的关键交互（开筛/结果渲染/本岗校准）建立冒烟用例；用 mock 的 Moka 页面 + mock LLM 走通端到端。目标：content.js 覆盖率提到 ≥60%。
  3. P0敏感信息审计与脱敏开关：新增"评分前脱敏"选项（姓名/手机/邮箱/身份证等字段替换为占位符），并在评分 prompt 明确"忽略占位符"；对发送给 LLM 的 profile 做字段白名单。这对内网/合规招聘场景是硬需求。
  4. P0统一失败可观测：给 background 增加结构化日志（请求 ID、耗时、provider、token 估算、缓存命中/未命中、重试次数），落 chrome.storage 环形缓冲区；侧栏设置页加"诊断信息导出"，遇到异常一键导出给维护者，替代现在的 console.log。

5.2 P1 · 中期提质

  1. P1拆分三个单体文件：content.js 按"接口拉取 / 硬门槛判定 / 评分流程 / Moka 自动化 / 消息路由"拆 5 个模块（复用 IIFE+UMD 模式，可直接被 Node 测试）；popup.js 按"岗位配置 / 结果列表 / 设置 / 校准"拆 4 个 render 模块；background.js 把"LLM 客户端 / 缓存 / 消息分发"分离。每个拆出模块配 20+ 断言测试。
  2. P1计分规则收敛成单一"规则引擎"：把 49/7/3/15/50/80、档位、加分晋级等集中到 lib/score.js 顶部配置对象 + 一张"输入→输出"决策表；prompt 与 UI 文案由规则引擎派生，避免五处各维护一份口径。为每次计分变更写"验收算例表"（现有 spec 已是雏形，工程化落地）。
  3. P1成本与用量看板：统计每轮筛选的 token 用量/预估费用（prompt 长度 × 单价可估算）、缓存命中节省额，侧栏显示"本轮预计消耗 & 已缓存省 X 元"；超预算阈值提醒，支持低档模型一键切换（结果精度 vs 成本的降级策略）。
  4. P1结果列表虚拟化与渲染节流：300+ 候选人时对结果 DOM 做窗口化渲染 + requestIdleCallback 批量更新，避免滚动卡顿；筛选进度条改为事件驱动而非全量重绘。
  5. P1异常恢复增强：为"拉取一半网络断 / Moka 接口限流 / 页面刷新"提供断点续拉（记录 lastCursor 与已评分集合，续筛只补缺）；对 Moka 接口 4xx/5xx 增加按接口级退避而非整轮失败。
  6. P1版本发布规范化：引入 CHANGELOG.md，manifest 版本与 README"当前版本要点"自动同步（脚本校验）；git tag 与 dist 产物对应；可选接 GitHub Actions 在 push 时跑全量测试 + 打包 artifact。

5.3 P2 · 长期演进

  1. P2模块化与配置化改造：向"配置驱动"演进——硬门槛、权重、加分项、档位阈值全部外置为 JSON Schema 配置（岗位级 preset 已有雏形），支持跨岗位复用模板库。
  2. P2Prompt 版本 A/B：支持同时配置两套 prompt（如严格/宽松），对同一批候选人并行打分，输出一致率与差异项，用数据驱动 prompt 迭代，而不是靠直觉改版。
  3. P2数据看板与洞察：沉淀多轮筛选历史，提供漏斗（投递→初筛→推荐→面试→Offer）、命中率、HR 与 AI 一致性趋势等分析，让插件从"筛人工具"升级为"招聘数据助手"。
  4. P2AI 面试辅助：基于候选人画像 + 岗位 JD 自动生成面试问题清单（技能深挖/经历追问/风险点验证），一键复制到面试流程。
  5. P2多 ATS 与国际化：将"Moka 适配层"抽象为适配器接口（接口模板捕获 + 页面操作），预留 BOSS/猎聘等扩展；界面支持中英双语。

七、结论与总体评分

总体评价：这是一个超出多数"自用插件"水准、工程完成度相当高的产品。它在 HR 招聘的真实痛点（批量初筛、门槛核对、匹配评估、反馈校准）上做得完整且细致：防串号、先证据后评分、门槛封顶、反馈学习闭环这些设计体现出对业务场景的深度理解；而 spec + TDD 计划 + 233 个单测的工程习惯，说明作者把"可验证"放在了很高的优先级。

主要短板不在功能与逻辑，而在工程化配套（无构建/lint/CI）与浏览器侧自动化测试缺失——随着功能继续膨胀，回归风险会集中在 content/popup 两个大文件上。建议按 P0→P1 节奏补齐工程底座并拆解单体文件，即可把当前"单点良好"升级为"可持续演进"。
